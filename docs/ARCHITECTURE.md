# System Architecture

## Overview
EPECPS follows a Clean Architecture pattern with clear separation between Domain, Application, Infrastructure, and API layers. The frontend is built with Angular following component-based architecture.

## Backend Architecture

**Components:**
- Entities: User, Role, Evaluation, Review, PersonalGoal, ScoreTemplate, etc.

### Design Patterns

**Repository Pattern**
- DbContext acts as repository
- Direct access through DbSet properties

**Service Pattern**
- Business logic encapsulated in service classes
- Interface-based dependency injection

**DTO Pattern**
- Separation between domain entities and API models
- Mapping between entities and DTOs

**Dependency Injection**
- Constructor injection throughout
- Service lifetime management (Scoped, Singleton, Transient)

### Authentication & Authorization

**Azure AD Integration**
- OAuth2 implicit flow for SPA
- JWT Bearer tokens for API
- Role-based access control (RBAC)

**Security Flow:**
```
1. User logs in via MSAL (Angular)
2. Azure AD returns access token
3. Token attached to API requests
4. API validates token with Azure AD
5. Claims extracted (user ID, roles)
6. Authorization policies enforced
```

**Role Hierarchy:**
- Admin: Full system access
- GM: Promotion decisions, all reports
- HOD: Department approvals, department reports
- RM: Review and approve evaluations
- TL: Conduct team reviews
- HR: Access reports, manage cycles
- Employee: Self-review, personal goals

### Data Access

**Entity Framework Core**
- Code-first approach
- Fluent API configurations
- Lazy loading disabled
- Explicit loading via Include()

**Connection Management**
- DbContext scoped to HTTP request
- Automatic connection pooling
- Transaction support

### Background Services

**Email Background Service**
- Hosted service for async email processing
- Queue-based processing
- Retry logic with exponential backoff
- Configured via EmailSettings

### Module Organization

**Core Module**
- Authentication configuration
- Guards and interceptors
- Singleton services
- Imported once in AppModule

**Shared Module**
- Reusable components
- Common directives and pipes
- Exported for use across features

**Feature Modules**
- Employee module (lazy loaded)
- Self-contained functionality
- Feature-specific routing

**Pages Module**
- Top-level page components
- Dashboard, login, error pages

### State Management

**Service-Based State**
- Services hold application state
- RxJS Observables for reactive updates
- BehaviorSubject for state broadcasting

**Local Component State**
- Component properties for UI state
- @Input/@Output for parent-child communication

### Routing Strategy

**Lazy Loading**
- Feature modules loaded on demand
- Reduces initial bundle size

**Route Guards**
- AuthGuard: Requires authentication
- RoleGuard: Requires specific roles
- Redirect to login if unauthorized

**Route Structure:**
```
/ ? Dashboard (requires auth)
/employee/evaluations ? Evaluation list
/employee/evaluations/:id ? Evaluation detail
/employee/goals ? Personal goals
/employee/approvals ? My approvals
/employee/reports ? HR reports
/unauthorized ? Unauthorized access page
```

### API Communication

**HTTP Interceptors**
- Attach access tokens to requests
- Handle errors globally
- Add retry logic

**Service Pattern**
- Dedicated service per API resource
- Typed responses with interfaces
- Observable-based async operations

### Authentication Flow

```
1. App initialization
2. MSAL checks for cached token
3. If no token, redirect to Azure AD
4. User authenticates
5. Redirect back with code
6. MSAL exchanges code for token
7. Token cached in localStorage
8. App proceeds to dashboard
```

## Communication Protocols

### API Endpoints

**Base URL**: https://localhost:7275

**Authentication**: Bearer token in Authorization header

**Content Type**: application/json

**Key Endpoints:**
```
GET    /api/evaluations
POST   /api/evaluations
GET    /api/evaluations/{id}
PUT    /api/evaluations/{id}
POST   /api/evaluations/{id}/submit-self-review
POST   /api/evaluations/{id}/tl-complete-review
POST   /api/evaluations/{id}/rm-approve
POST   /api/evaluations/{id}/hod-approve
POST   /api/evaluations/{id}/gm-approve
GET    /api/personal-goals
POST   /api/personal-goals
PUT    /api/personal-goals/{id}
GET    /api/dashboard/stats
POST   /api/reports/evaluations/export
```

### Error Handling

**HTTP Status Codes:**
- 200: Success
- 201: Created
- 400: Bad Request
- 401: Unauthorized
- 403: Forbidden
- 404: Not Found
- 500: Internal Server Error

**Error Response Format:**
```json
{
  "error": "Error message",
  "details": "Detailed error information"
}
```

## Deployment Architecture

### Development Environment
```
Frontend: http://localhost:4200 (ng serve)
Backend:  https://localhost:7275 (dotnet run)
Database: LocalDB or SQL Express
SMTP:     Gmail/Office365 (dev credentials)
```

### Production Environment
```
Frontend: Azure Static Web Apps / CDN
Backend:  Azure App Service / Container
Database: Azure SQL Database
SMTP:     SendGrid / Office365
Auth:     Azure AD (production tenant)
```

## Security Considerations

**Authentication**
- Azure AD OAuth2 tokens
- Token expiration and refresh
- HTTPS only in production

**Authorization**
- Role-based access control
- Policy-based authorization
- Claims-based identity

**Data Protection**
- SQL injection prevention (parameterized queries)
- XSS prevention (Angular sanitization)
- CSRF protection (SameSite cookies)

**Secrets Management**
- appsettings.json for development
- Azure Key Vault for production
- Environment variables for sensitive data

## Monitoring & Logging

**Backend Logging**
- Serilog for structured logging
- Log levels: Debug, Information, Warning, Error
- Audit logging for critical operations

**Frontend Logging**
- Console logging in development
- Application Insights in production

**Performance Monitoring**
- SQL Server query performance
- API response times
- Frontend bundle sizes
